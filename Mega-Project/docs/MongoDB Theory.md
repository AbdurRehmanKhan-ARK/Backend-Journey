 # MongoDB Theory

A reference covering MongoDB concepts from the ground up through aggregation pipelines. Written to explain terminology and reasoning, not just syntax to copy.

---

## 1. What MongoDB Actually Is

MongoDB is a NoSQL, document oriented database. Instead of storing data in rows and tables like a relational database (MySQL, PostgreSQL), MongoDB stores data as documents inside collections.

| Relational Term | MongoDB Equivalent |
|---|---|
| Database | Database |
| Table | Collection |
| Row | Document |
| Column | Field |
| Primary Key | `_id` |
| Foreign Key | ObjectId reference |

A document is stored in a format called BSON (Binary JSON), which is a binary representation of JSON with extra data types like `ObjectId`, `Date`, and `Long` that plain JSON does not support natively.

**Why document oriented matters:** a single document can hold nested objects and arrays directly, so related data can often live together in one place instead of being split across many tables and joined together at query time.

---

## 2. Documents and Collections

A document looks like this:

```json
{
  "_id": ObjectId("64f1a2b3c4d5e6f7a8b9c0d1"),
  "username": "abdur_123",
  "email": "abdur@example.com",
  "createdAt": ISODate("2026-01-01T00:00:00Z")
}
```

A collection is simply a group of documents, roughly equivalent to a table. Unlike a relational table, a collection does not enforce a rigid schema by default. Two documents in the same collection can technically have completely different fields, though in practice an ODM like Mongoose is used to enforce a consistent shape at the application level.

`_id` is automatically generated by MongoDB unless explicitly provided, and it functions as the unique identifier for every document, similar to a primary key.

---

## 3. Schemas and Mongoose

MongoDB itself does not require a schema. Mongoose (the ODM used in this project) adds schema enforcement on top of MongoDB, so the application can define what shape a document should have before it ever reaches the database.

```javascript
const userSchema = new Schema({
  username: { type: String, required: true, unique: true },
  age: { type: Number },
});
```

Key terminology:
- **Schema**: the blueprint describing fields, types, and validation rules
- **Model**: a compiled version of a schema, used to actually create/read/update/delete documents (`mongoose.model("User", userSchema)`)
- **Document**: an actual instance of data created from a model

---

## 4. CRUD Operations

CRUD stands for Create, Read, Update, Delete, the four basic operations any database needs to support.

| Operation | MongoDB Shell | Mongoose |
|---|---|---|
| Create | `db.users.insertOne({...})` | `User.create({...})` |
| Read | `db.users.find({...})` | `User.find({...})`, `User.findOne({...})`, `User.findById(id)` |
| Update | `db.users.updateOne({...}, {$set: {...}})` | `User.findByIdAndUpdate(id, {...})` |
| Delete | `db.users.deleteOne({...})` | `User.findByIdAndDelete(id)` |

**Common update operators:**
- `$set` sets the value of a field
- `$unset` removes a field entirely from the document
- `$inc` increments a numeric field by a given amount
- `$push` adds an item to an array field
- `$pull` removes an item from an array field matching a condition

---

## 5. Query Operators

Queries filter documents using operators, most of which start with `$`.

| Operator | Meaning |
|---|---|
| `$eq` | equal to |
| `$ne` | not equal to |
| `$gt` / `$gte` | greater than / greater than or equal |
| `$lt` / `$lte` | less than / less than or equal |
| `$in` | value exists in a given array of options |
| `$or` | matches if any condition in the array is true |
| `$and` | matches if all conditions in the array are true |
| `$exists` | field is present (or absent) on the document |

Example, used in this project's login logic to check either identifier:

```javascript
User.findOne({ $or: [{ username }, { email }] });
```

## 6. Relationships: Embedding vs Referencing

Since MongoDB is not relational, there is no built in JOIN the way SQL has one. Related data is connected in one of two ways.

### Embedding

Nested data lives directly inside the parent document.

```json
{
  "username": "abdur_123",
  "address": { "city": "Karachi", "zip": "75500" }
}
```

Good for data that is always accessed together and does not grow unbounded (an address inside a user document, for example).

### Referencing

The related document is stored separately, and the parent document stores only its `ObjectId`, similar to a foreign key.

```javascript
watchHistory: [{ type: Schema.Types.ObjectId, ref: "Video" }]
```

Referencing is the right choice when the related data can grow very large (a channel's list of subscribers, for example, as covered in the Subscription schema notes), when the related data is shared across many documents, or when the related data needs to be queried independently.

**Populate**, a Mongoose specific feature, resolves a referenced `ObjectId` into the actual document data at query time:

```javascript
const video = await Video.findById(id).populate("owner");
// video.owner is now the full User document, not just an ObjectId
```

## 7. Indexes

An index is a data structure that makes queries on a particular field dramatically faster, at the cost of some extra storage and slightly slower writes (since the index has to be updated on every insert/update too).

Without an index, MongoDB has to scan every single document in a collection to find matches, a full collection scan. With an index, it can jump directly to matching documents.

```javascript
username: { type: String, index: true }
```

`unique: true` on a schema field also creates an index, which is what actually enforces the uniqueness constraint at the database level (registration duplicate checks in this project rely on this).

## 8. Aggregation Pipeline

The aggregation pipeline is MongoDB's framework for processing documents through a sequence of stages, where each stage transforms the data and passes the result to the next stage. It is far more powerful than a simple `find()` query and is what makes complex reporting, joins, and computed fields possible.

The general shape:

```javascript
Model.aggregate([
  { stage1 },
  { stage2 },
  { stage3 },
]);
```

Data flows through stages like a pipe, each stage receiving the output of the one before it.

### Common Stages

**`$match`**: filters documents, works like the `find()` query filter. Almost always placed early in the pipeline to reduce the number of documents flowing into later, more expensive stages.

```javascript
{ $match: { username: "abdur_123" } }
```

**`$project`**: reshapes each document, choosing which fields to include, exclude, or compute.

```javascript
{ $project: { username: 1, email: 1, _id: 0 } }
```

**`$group`**: groups documents by a given field and computes aggregated values (count, sum, average) per group, conceptually similar to `GROUP BY` in SQL.

```javascript
{
  $group: {
    _id: "$channel",
    subscriberCount: { $sum: 1 },
  },
}
```

**`$lookup`**: performs a join against another collection, the closest MongoDB equivalent to a SQL JOIN. This is essential for a schema like the Subscription model, where subscriber counts live in a separate collection from the User documents themselves.

```javascript
{
  $lookup: {
    from: "subscriptions",
    localField: "_id",
    foreignField: "channel",
    as: "subscribers",
  },
}
```

**`$addFields`**: adds new computed fields to each document without removing the existing ones, often used right after a `$lookup` to turn a joined array into a usable count.

```javascript
{
  $addFields: {
    subscriberCount: { $size: "$subscribers" },
  },
}
```

**`$sort`**: orders documents by a given field, `1` for ascending, `-1` for descending.

```javascript
{ $sort: { createdAt: -1 } }
```

**`$limit`** and **`$skip`**: used together for pagination, `$skip` moves past a number of documents and `$limit` caps how many are returned after that.

```javascript
{ $skip: 10 },
{ $limit: 5 },
```

### Full Example: Subscriber Count for a Channel

Tying together the Subscription schema concept with an actual aggregation:

```javascript
Subscription.aggregate([
  { $match: { channel: channelId } },
  {
    $group: {
      _id: "$channel",
      subscriberCount: { $sum: 1 },
    },
  },
]);
```

This matches all subscription documents pointing at a given channel, then groups them and counts how many exist, which is exactly the manual counting logic described in the Subscription schema notes, just expressed as a single database side operation instead of pulling all documents into the application and counting there.

⭐ **Interview point:** aggregation pipelines run inside the database engine itself, which is significantly faster than fetching raw documents and computing counts/joins in application code, especially as collections grow large.

## 9. Transactions

For operations that must succeed or fail as a single unit (multiple related writes across documents, where a partial failure would leave the database in an inconsistent state), MongoDB supports transactions, similar in concept to SQL transactions.

```javascript
const session = await mongoose.startSession();
session.startTransaction();
try {
  await User.create([{ ... }], { session });
  await Subscription.create([{ ... }], { session });
  await session.commitTransaction();
} catch (error) {
  await session.abortTransaction();
} finally {
  session.endSession();
}
```

Transactions require a replica set in MongoDB (a single standalone instance does not support them), which is worth knowing when setting up a local development database versus a production one.

## 10. Quick Terminology Reference

| Term | Meaning |
|---|---|
| Document | A single record, stored as BSON |
| Collection | A group of documents, roughly a table |
| Field | A key inside a document, roughly a column |
| ObjectId | MongoDB's default unique identifier type for `_id` |
| Schema | The application level blueprint for document shape (Mongoose concept) |
| Model | A compiled schema used to interact with a collection |
| Populate | Resolving a referenced ObjectId into full document data |
| Index | A structure that speeds up queries on a given field |
| Aggregation Pipeline | A sequence of stages that transform documents |
| Stage | A single step in an aggregation pipeline |
| Embedding | Storing related data directly inside a parent document |
| Referencing | Storing only an ObjectId link to a separate document |
